## 判据（沿用项目规矩）

- **镜像 A/B**：同一个 walk-through harness、同一批种子、双先后手（`firsts=e,p × asides=e,p`）、
  两边都打同一支陪练副本（`opp=base` = `RL/ai/AI_Battle_原版.gd`）。
- 臂之间**只差权重文件里的键**（`base_weights = RL/weights/噩梦.json` + theta 叠加）⇒ 归因干净。
- 「≤5 队的读数不可信」（项目翻车过 6 次）⇒ 单批至少 4~5 队或等量的**种子多样性**。
- 判据 = 配对 **Δpts 的 95% CI 不跨 0** 才算有结论；跨 0 记「无差异」。

## 操作入口

```powershell
# 造候选权重（theta = 相对 噩梦.json 的覆盖）
powershell -NoProfile -ExecutionPolicy Bypass -Command "& 'RL\train\Train.ps1' -Task gen -Run nm1_A -Spec 'RL\train\spec_nm1_A.json' -Configs n_ctrl,n_esc,..."
# 跑批（resume-aware：同 Run 再跑会跳过已测格子）
powershell -NoProfile -ExecutionPolicy Bypass -Command "& 'RL\train\Train.ps1' -Task run  -Run nm1_A -Spec 'RL\train\spec_nm1_A.json' -Configs ... -SeedSet train -MaxSeeds 16 -Firsts e,p -Asides e,p"
# 配对比较
powershell -NoProfile -ExecutionPolicy Bypass -Command "& 'RL\train\Train.ps1' -Task compare -Run nm1_A -Spec 'RL\train\spec_nm1_A.json' -Configs ..."
```

规格：`RL/train/spec_nm1_A.json`（= `spec_teamA.json` 的副本，只换 `configs`）。

## ⚠️ 已踩的陷阱（务必记住）

1. **`-FixedDecks` 不加 ⇒ 阵容是按种子随机抽的**。
   我第一版建了 `spec_nm1_A..E.json` 五个规格当"5 支队"，但没加 `-FixedDecks`
   ⇒ 五个 run 跑的是**同一批对局**（实测：`nm1_A` 与 `nm1_B` 的 `measure.csv` 前 3 行逐位相同 ——
   同 seed 10001、同 round 833、同 `lineup_used=hero_09,hero_40,hero_22`）
   ⇒ **5 倍时间买 1 份数据**。
   ⇒ 正确做法二选一：**① 单 spec + 多个种子**（种子多样 = 阵容多样，配对仍有效，本文采用）；
   **② 多 spec + `-FixedDecks`**（每个 spec 固定一支队，才是 `多队伍评估.ps1` 的设计口径）。
2. **`-Task estimate` 需要先有实测行**（新 run 直接用会 `FATAL: has no measured rows yet`）
   ⇒ 先跑一小批（2 种子）再估。
3. 吞吐：beam 200 ⇒ 实测 **24~42 s/局**。**`-Workers` 默认 1（串行！）** —— 一个"每臂 64 局"的
   标准批串行要 1.5~2.5 小时，**加 `-Workers 6` 后并行 6 格 ⇒ ≈25 分钟**。日志里 `[slot] free (round 1; running 0/1)`
   就是"只开了一个槽"的证据。⚠️ 项目自己的 `难度体检.ps1` 默认就是 `-Workers 6`，所以这是我们用错了入口，不是设施限制。
4. **`RUNNING.lock`**：`RL/train/results/<run>/RUNNING.lock` 里写着 `pid=…` 与启动时间。
   批被中途杀掉（或超时）后锁会**留在盘上**，下一次同 run 直接
   `FATAL: RUN LOCK … exists (age X min)` 拒跑 —— 而 resume 机制本来就是为了"接着跑"。
   ⇒ 判据 = **锁里的 pid 进程不存在**才删（我的做法：读 pid → `Get-Process -Id` → 不存在就 `Remove-Item`）。
   ⚠️ PowerShell 里别把变量命名成 `$pid`（只读自动变量，赋值静默失败 ⇒ 会拿到当前进程 id、误判"锁还活着"）。
5. **杀批之后要顺手清 headless Godot**：任务被 kill 时 `cmd`/`powershell` 死了，Godot 子进程不一定会跟着死
   （`跑Godot隔离.ps1` 里那段"按没有窗口标题"清理就是为此）。判据：**只杀 `MainWindowTitle` 为空的**，
   绝不碰用户开着的编辑器/游戏。

### ⚠️ 陷阱 6：`opp=base` ≠ 难度3

`spec` 里 `"opponent": "base"` 的对手是 **`RL/ai/AI_Battle_原版.gd` + difficulty=2 = 困难口径**，
**不是难度3**。要"难度4 打难度3"必须在 spec 里加：

```json
"league": { "self_play_fraction": 1.0, "checkpoint": "RL/weights/噩梦.json" }
```

⇒ `opp=cand` ⇒ 对手也走同一个 fork（`RL/ai/AI_Battle.gd`），只是 `set_weights(噩梦.json)`；
`self_play_fraction=1.0` ⇒ 每个格子都对上 checkpoint（不是抽一部分）。日志会打
`[league] self-play cells=N base cells=0 fraction=1 checkpoint=RL/weights/噩梦.json sha12=…`。

### ⚠️ 陷阱 7：多臂批的"对手一致性"守卫

runner 会拒：`LEAGUE ARM MISMATCH: the same (seed, first) is played against DIFFERENT opponents by different configs`
—— 它把 **(opp, checkpoint_sha, beamB)** 当成对手身份，而 beam 扫描的三个臂 `beamA` 不同时它算出的 `beamB` 也跟着变
（实测 `cand/c12a3c68167f/100` vs `/200` vs `/50`）⇒ **beam 扫描只能"一臂一 run"**。
（`opp=base` 的多臂批不受此限，因为对手身份恒为 `base`。）

### ⚠️ 陷阱 8：缺格的批会被拒合并

走查台的 `time_budget_ms = 0`（**不限时**，为了可复现）⇒ 个别格子能跑到 **30+ 分钟**（实测 3 格）。
整批结束时 runner 打 `Invoke-ParallelCells: only 9 of 10 worker(s) reported a result; refusing to merge`
⇒ **它不写顶层 `measure.csv`**。解法：① 每格给 `-TimeoutSec 900` 兜底；
② **读数自己聚合**：`RL/train/results/<run>/{measure.csv, w*/measure.csv}` 去重后统计（脚本 `.dsh/tmp/agg_multi.py`）。

## 下一步：**增加深度**（用户口径 2026-10-02「你增加深度」）

### 为什么现在的"深度"是假的

`search()` 只搜**本回合**（我方各单位各行动一次），末态用 `_evaluate(sim, end_of_turn=true)` 打分；
对手的下一回合**不模拟**，只有一把解析式估计 `_incoming_total_on()`（每个敌人各算一次"走过去打"）。
它缺三样：**目标优先级**（对面会挑能杀的那个集火）、**连杀链**、**我方的再反击**。

### 技术阻塞（必须先解决，否则重复当年那个 bug）

`_evaluate()` **不是对称的**：`②身价` 写死 `u.fn == ENEMY` 为"我方"、对面还要 ×`PLAYER_VALUE_MULT(1.25)`。
⇒ 直接 `search(sim, PLAYER)` 让对手用我们的评估挑招，等于**让对手替我们着想** ——
这正是当年"真推演"把「对面会来打我们」判成 0 的原因（过度乐观）。

### ✅ 已落地：方案 2「贪心报复法」＝ `REPLY_PEEK`（2026-10-02）

两条候选里选了**第 2 条**（第 1 条 relabel 法要处理 `active_fn`/`engaged0`/`my_dead`/`foe_dead`
这些**按阵营缓存**的字段，漏一个就静默错 ⇒ 风险不对称，先不做）。

- **落点**：`_search_two_phase()` 的收尾（**两阶段路径**，现役档位走的就是这条）。
  收集器在阶段 2 的完态循环里（只 append 引用，不排序、不克隆）；收口在 `_reply_rerank()`。
- **对手模型**（`_reply_turn_score()` / `_reply_step_value()`）：克隆末态 → **当作对手回合开始**
  （显式复位对手的 `moved/attacked`、两边都复位 `counter_used` —— 真实侧 `Battle.gd` 切回合时对
  **所有**单位调 `Unit.reset_for_new_turn()`；不复位就会踩"对面显示已行动 ⇒ 一手不出 ⇒ 静默失效"）
  → 每个还能动的敌方单位按**阵营中立净值**挑一手（`掉血 1 点 = 1 分`；打死再加 `2.0 × 该单位攻击力`）
  → 全部走完，最后交回 `_evaluate(s, true)` 排序。⚠️ **对手挑招绝不用 `_evaluate`**（阵营不对称）。
- **不吃 `TIME_BUDGET_MS` 的余额**（只受 `abort_requested` 约束）：否则**最难的回合**（正是最该看
  对手一眼的回合）会因为搜索把预算用光而一个末态都瞥不到 ⇒ 键在最该生效处静默失效。
- **键名不叫 `REPLY_TOPK`**：那个名字 **2026-09-20 已判死**（rp4 Δ−0.45 / rp8 +1.74）并登记在

## ⚠️ 陷阱 10：**BOM-less `.ps1` + 中文注释 = 定时炸弹**（2026-10-02 实测踩中）

**症状**：`Train.ps1 -Task gen` 直接 `FATAL: ParseException :: At RL\train\RlTrain.ps1:1571 char:29`，
`-Task run` 同样报 ⇒ **整条训练链不可用**。

**根因**：`RL/train/RlTrain.ps1` 是 **UTF-8 无 BOM**，而 `Train.ps1` 是用 **Windows PowerShell 5.1** 起的
⇒ PS 5.1 按 **ANSI(GBK)** 解码 ⇒ 中文注释的 UTF-8 字节里有**落在 GBK 前导字节区间的续字节**，
会把**该行末尾的换行吃掉**（非法双字节对被当成一个替换字符合并）⇒ **多行注释被并成一行**，
于是那一行末尾的 `#` 把**后面真正的代码**（数组收尾 `]` 与函数结尾 `}`）整段注释掉 ⇒ 只剩一个裸 `}`。

**这次是谁踩的**：隔壁会话往这个文件里插了 `LAST_MAN_W` 的 7 行中文注释（1572~1578）⇒
ANSI 视角下它们被并成 **582 字符的一行**、末尾正好是 `#`，1573 行变成 `}` ⇒ 炸。
（同文件里原有的中文注释一直没事，只是**运气好**——被并的行都没吞掉代码。）

**修法（已落地）**：给 `RlTrain.ps1` **加 UTF-8 BOM**（`EF BB BF`）⇒ PS 5.1 认出是 UTF-8、按 UTF-8 解码
⇒ 解析错误 **0**、中文注释全部保留、**零行为改动**。⚠️ **不要再把 BOM 去掉**。

**顺带扫出同款未爆的雷**（`RL/train` 下 BOM-less 且含中文的 .ps1）：
`多阵容搜索.ps1`（中文 1368 字）· `联合搜索.ps1`（中文 1559 字）
⇒ **要跑它们之前先加 BOM**（或把中文注释 ASCII 化）。**没动它们**（不在本次路径上，等用户点头）。

**怎么预防**：新写/新插中文注释进 `.ps1` 时，① 先确认该文件有 BOM；② 或者注释全用 ASCII
（`RlTrain.ps1` 文件头原本就写着"不要把中文塞进这个脚本"，是这次被越过的约定）。

### 与 beam 的关系（⚠️ 2026-10-02 修正：前提不成立）

原设计写的是「竞品 beam 48 + depth 6，我们 beam 400 + depth 1 ⇒ 先证明 beam 能降到 100/50 不掉强度，
再把省下的算力投给深度」。**前半句不成立** —— beam 在我们这里是**死键**（逐位相同，不是"无差别"）：
`w_beam` 全文只有两个消费者（`_search_two_phase()` 的 `p1_beam` 与 `inner`），而两条都被
`TWO_PHASE_P1_BEAM = 96` / `TWO_PHASE_INNER = 16` 绕开了；旧束搜索那条路在 `SEARCH_MODE ≥ 1` 时
**根本走不到**。⇒ **"砍 beam 换深度"这个交易在我们引擎里不存在**（beam 本来就没在花算力）。
真正的算力旋钮（想省思考时间就动它们）：`TWO_PHASE_P1_BEAM` · `TWO_PHASE_INNER` ·
`TWO_PHASE_LAYOUTS` / `SUMMON_LAYOUTS` · `TIME_BUDGET_MS`。深度这边照旧照做（批次6）。

| `n_tb2` | `TIEBREAK_MODE = 2` | **威胁差并列裁决**：分差 < `TIEBREAK_EPS(0.5)` 时按 ①我方阵亡 ②对方阵亡 **③威胁差（Σ我方威胁 − Σ对方）** ④血差 ⑤最残血 排序 |
| `n_esc_tb2` | 两者 | 叠加 |

### 为什么挑这两个（对照竞品 AI）

- 竞品最强的一块是**位置与"剥夺"计价**（它的 6.4MB 网络里最大一组特征就是 `(英雄, 阵营, 格子)` 一热）。
  我们这边**"让对方打不满"这一维在账本上是 0 分**（探针 `RL/自进化/probe/对方总输出自检.gd`：把玩家火枪手的
  输出从 4.0 压到 1.0，`_evaluate` 最好只值 +0.71、常见是 **−5.46**，因为 ㉑ 对贴脸收 −6.00）。
  ⇒ `n_esc` 拆掉那笔税；`n_tb2` 用引擎**已经算好、却一直关着**的"威胁差"把这一维接回来。
- `TIEBREAK_MODE` 在 `噩梦.json` 里**根本没写** ⇒ 四档现役的并列裁决是**整段关的**（引擎默认 0）；
  代码注释里写着「探针显示 **98% 的局面相差 < 5**」⇒ 并列裁决不是小事。
  它**只用于拆并列、不进评分** ⇒ 不会像被判死的 `THREAT_INCOMING_W` 那样奖励"各自躲"。
