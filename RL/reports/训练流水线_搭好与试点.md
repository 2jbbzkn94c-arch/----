## 1. 「原版副本是否同源」的验证方法与结论

### 1.1 为什么必须先验

整个训练/验收的**对手口径**都建立在「`RL/ai/AI_Battle_原版.gd` = 生产困难档 AI」上：
`对局.gd` 的 `opp=base` 分支只做 `BASE.new(_b.grid)` + `difficulty = 2`，如果副本与
`src/BattleAI.gd` 不同源，那么「噩梦 vs 困难」测的就不是生产口径，后面全部白测。

### 1.2 归一化规则（逐字复述，可复现）

1. 两侧都用 UTF-8 读全部行；
2. **删掉所有空白行**（含只含空白的行）；
3. 每行**去掉行尾空白**（保留行首缩进 —— 缩进本身参与比对）；
4. `src/BattleAI.gd` 去掉第 1 行 `class_name BattleAI`；
5. `RL/ai/AI_Battle_原版.gd` 去掉开头 4 行头注释（`## 【RL 陪练副本】…` 起的 4 行）；
6. 剩余行按顺序拼接（每行尾补 `\n`），算 UTF-8 字节的 SHA-256。

### 1.3 结论

| 项 | src/BattleAI.gd | RL/ai/AI_Battle_原版.gd |
|---|---|---|
| 文件总行数 | 1735 | 1738 |
| 有效行数（去空行/去行尾空白后） | 1668 | 1671 |
| 归一化后正文行数 | **1667** | **1667** |
| 正文 SHA-256（UTF-8，行尾 `\n`） | `f48faff579928933936dd41edabf54f9beb3d65ffda7c745c3afe1d18617588c` | `f48faff579928933936dd41edabf54f9beb3d65ffda7c745c3afe1d18617588c` |

* `git diff --no-index` 的差异块**只有 1 处、共 5 行**：src 侧 1 行 `class_name BattleAI`，
  副本侧 4 行头注释。
* **正文逐行逐字节相同 → 差异行数 = 4（均为头注释）+ 1（刻意去掉的 `class_name`）。**
* 副本的 `difficulty` 语义已复核：`AI_Battle_原版.gd` L387-398 —— `difficulty >= 2` 时
  `_beam()` 返回 **800**、`_jitter()` 返回 **0.0**，与生产「困难档」一致。

> **结论：同源成立，`opp=base` 作为“生产困难档陪练”的口径可以使用。**

## 2. 权重 JSON 可接受 schema

由 `RL/ai/AI_Battle.gd::set_weights()`（L312-336）/ `set_hero_weights()`（L341-359）/
`_hero_value()`（L362-365）**只读**得出：

### 2.1 顶层 12 个通用键（值必须是数字，int/float 均可）

| 键 | 语义 | 范围/量级建议 |
|---|---|---|
| `KILL_BONUS` | 本回合击杀数 × 此值 | ~35 |
| `FOCUS_FIRE_WEIGHT` | `frac² × 此值`，同一目标已掉血比例越高越倾向继续打 | ~30 |
| `GOLD_TAKE_VALUE` | 吃 1 枚金矿的分值（高攻单位） | ~26 |
| `GOLD_TAKE_VALUE_LOW` | 吃 1 枚金矿的分值（低攻单位） | ~34 |
| `GOLD_LOW_ATK` | 判定「低攻」的攻击力阈值 | 整数 ~4 |
| `BUFF_TAKE_WEIGHT` | 吃增益道具的分值权重 | ~3 |
| `THREAT_MOVE_DISCOUNT` | 「要先移动才能打到」那份威胁的折算系数 | 0~1 |
| `OBSTACLE_DETOUR_WEIGHT` | 障碍挡路造成的绕路代价分值（驱动拆墙） | ~4 |
| `ENGAGE_PULL_PER_CELL` | 够不到敌人时每格的压上拉力 | ~1.2 |
| `MAX_MOVE_OPTIONS` | 每单位每回合保留的候选走位数 | 整数 ~16 |
| `BEAM` | 搜索波束宽度（**算力**，不是评分倾向） | 困难档 800；噩梦档 1200 |
| `JITTER` | 决策抖动幅度（0 = 纯最优、可复现） | 困难档 0.0 |

### 2.2 唯一嵌套段 `HERO_VALUE`

```json
"HERO_VALUE": { "hero_22": 1.35, "hero_40": 0.9 }
```

* 被 `set_weights` 特判后转给 `set_hero_weights`，写入 `w_hero_value`；
* `_hero_value(hero_id)` 的优先级：**注入值 > 内置 `HERO_VALUE_DEFAULT` > 1.0**；
* ⚠️ **只写部分英雄时，未写的英雄仍走内置默认表**（不是 1.0）。要显式压成 1.0 必须逐个写
  （`RL/weights/全1对照.json` 就是 49 个全写 1.0）；
* 它乘进 `_unit_value()` 的 base，因此同时影响「打它的优先级」和「保它的意愿」。

### 2.3 容错行为（决定了我们敢不敢直接写候选文件）

* **未知键静默忽略**；值不是数字**静默跳过**；`_` 开头的说明键天然被忽略
  （所以 `噩梦.json` 里的 `_说明/_替换方法/_键位含义/...` 全部无害，可原样继承）；
* `set_hero_weights` 另支持 `{ "hero_42": { "GOLD_TAKE_VALUE": 40.0 } }` 这种「按英雄覆盖通用键」
  的形式，但 `对局.gd` 只经 `set_weights` 注入，**该路径当前用不到**；
* 我们生成的候选一律写到 **`RL/weights/cand_<Run>_<Config>.json`**，
  `噩梦.json` / `全1对照.json` / `基础.json` / `base.json` 全程只读。

### 3.5 试点暴露出的四个结论（每个都能追到上面的原始行）

**(1) 四个 seed/阵容组合上，候选的全部 4 局都赢，且是「逐步打赢」而不是一波决胜。**
`rounds` = 19/17/11/21，`killsA=3`，`over=true` —— 与上一轮在旧阵容上看到的
`rounds=0` 一波决胜完全不同。说明**阵容轮换把测量从「谁先手谁赢」拉回到真实对局**，
这正是 §4 设计要的效果。

**(2) `KILL_BONUS` 35 → 70 在这 4 个观测上零差异，而且是逐字段完全相同。**
两个配置的 4 行 `res/rounds/ptsA/ptsB/dmgA/dmgB/hpA/hpB` 全部一致。
两种解释必须靠实验区分：
* (a) `KILL_BONUS` 对这 4 局的决策确实没有影响（集火/走位决定了结果，击杀奖励没改选点）；
* (b) **权重没真正注入**（例如文件路径没传到 A 方）。
* **本轮无法区分**——`R|cfg|` 行只打印了两个脚本的 SHA，**没有打印权重文件的内容哈希**。
* 已列为阶段 1 开始前的必修项：让 A 方把 `w_kill_bonus` 等生效值**回显**到 stdout
  （不改 harness 的话，用「同一 seed 下两个差异极大的权重是否给出不同 `R|m|`」的
  对照实验代替，例如 `JITTER`=0 与 0.5、`BEAM`=200 与 2400）。

**(3) 可复现性得到一次强证据。** 试点中我曾误触发重跑（`-Force` 语义之外的重复执行），
`b_base_s10001_fe` 被重跑了两次：两次的 `R|m|` 4 行**逐字节相同**，`search_ms_max` 5587 vs 5587、
`wall_s` 52.4 vs 52.2。这是「固定种子 + `JITTER=0` → 同权重同结果」的直接证据
（也是我敢把 `JITTER` 保持 0 的理由）。

**(4) 墙钟是**双峰**的，这直接推翻了我原来的预算估计。**
* 快批（seed 10001）：2 局 **53 秒** → **26.5 s/局**，`search_ms_max` ≈ 5.5s；
* 慢批（seed 10002）：2 局 **242 秒** → **121 s/局**，`search_ms_max` = **38.6~38.8s**（单次搜索！）。
* 差 4.6 倍的原因就是**个别局面下 beam=1200 的搜索爆炸**（单次 search 38.8s），
  与 `对局.gd` 的 `time_budget_ms = 0`（不限时、自然搜完）叠加。
* 实测总账：试点 8 局 + 4 次 Godot 启动 = **9.9 分钟**（592s）；
  折算 **≈74 s/局**（含启动），**不是我原先估的 8~12 s/局**。

## 4. 阵容池设计（覆盖 49 个英雄，训练/留出组合不重叠）

### 4.1 确定性生成器（不改 harness，只用命令行 `edeck/pdeck` 覆盖）

```
round r = floor(seed / 12)
slot  j = seed mod 12
stride = strides[(r + j) mod 12]        # 每个 slot 在不同 round 换 stride，避免只有 12 套阵容
阵容 = [ (i*stride + r) mod 49 + 1 ]  for i = j, j+1, j+2   → 3 个 hero_id
```

* 同一个 slot 内，连续 49 个 round 会把 49 个英雄各覆盖一次；
* 偶数 seed → 生成阵容给**敌方**，奇数 seed → 给**玩家**（两侧都在轮换）；
* 另一侧用 **anchor 轮换**（A/B/C 三套固定阵容），`anchor = anchors[(r+j) mod 3]`。

### 4.2 两个池子的 stride（由离线搜索得出，脚本内写死）

| 池 | strides | 说明 |
|---|---|---|
| 训练池 | `11,3,29,19,37,15,39,25,45,27,31,1` | `Find-Strides.ps1` 搜索 200k 组，`min hero coverage = 3`（118 组试验内最优） |
| 留出池 | `1,29,39,33,25,15,9,31,17,47,3,13` | `Find-HoldoutStrides.ps1` 搜索 disjoint 组，与训练池 **零重合** |

### 4.3 覆盖与不相交自检结果（`-Task coverage` 输出，可复现）

```

distinct lineups: train=105, holdout=24, overlap=0        (must be 0)
```

**⚠️ 一个必须纠正的口径问题：`beam_200` 的配对只有 6 对。**
`对局.gd` 打印的 `a_side` 是**批内局序号**（不是阵营），所以"配对"实际按**局序**配对；
`beam_200`/seed 10004 的第 2 局变成平局（原本是 W），于是按 `a_side` 配对时少了一对。
不影响"降档不显著变差"的结论，但确认了 **`a_side` 不能当配对键**；主键已改为
`(config, seed, first, seq)`（§8 第 6 条）。

**结论与建议**：
1. **训练档用 `beam=400`**（省 26% 墙钟，胜率配对不显著变差）；保守一点用 600（省 23%）。
   `beam=200` 省 37% 但样本里出现平局、配对不完整，**在更大样本验证前不建议采用**。
2. **验收档保持 1200**（一次性考卷不该省算力）。
3. **降档省不了想象中那么多**：`BEAM` 降 3 倍只省 26%，因为**单次搜索耗时里有与 beam 无关的
   固定成本**。实测 seed 10002 的 `search_ms_max` 在 1200/600/400/200 下几乎不变
   （39276 / 39125 / 39150 / 39252 ms）→ 瓶颈是搜索过程本身（单位扩展 + 局面拷贝），不是波束宽度。
4. **下一步真正该压的是单次搜索的固定成本**，候选手段（都不需要改冻结文件）：
   * `MAX_MOVE_OPTIONS` 16 → 8（**它同时是评分参数**）：直接砍分支因子，预计收益比降 beam 大；
   * 先把「一局内最大 `search_ms` 的分布」量出来，找出为什么某些局面要 39 秒；
   * 训练用 `beam=400`，只在**留出验收**用 1200。

### 7.3 顺带发现的设计缺陷：**19% 的训练种子把同一个英雄放在了两边**

  并在 `-Task coverage` 里加一条 `anchor ∩ generated == ∅` 的检查。
* 本轮的 pilot / inj / beamsweep 结论**不受影响**（撞车只影响 HERO_VALUE 的解释，
  不影响算力档位与胜率比较）。

## 9. 并行提速与 5v5 静态结论

### 9.1 多 worker 并行（`-Workers K`）：代码已实现，**等价性尚未验证**

已实现（全部在 `RL/train/**`，未碰冻结文件）：

* `-Workers K`（默认 6，上限 10，留余量给用户玩游戏）；
* **每 worker 独立隔离**：独立 `APPDATA` 沙箱（→ 独立 `user://`，避免两个实例抢
  `user://logs` 导致 signal 11）、独立 `results/<run>/w<k>/`（**绝不并发写同一张 `measure.csv`**）、
  独立 `.out` / `.godot.log` / `.jobpid` / `.godotpid`；
* **只杀自己记录的 PID**：每批在启动瞬间把 Godot 子进程 pid 写进 `b_*.godotpid`，
  超时只杀这个 pid 与自己的 job host pid。**已彻底移除"按启动时间/进程名筛选"的启发式**——

  **一个 Godot 都没启动过**，所以按时间筛"我的进程"从原理上就是错的。
* **分区单元 = (config, seed)**：整块分给同一 worker。这样续跑主键 `(config, seed, first, seq)`
  语义不变，配对单元 `(seed, first, seq)` 也不会被拆散 → **worker 数不影响配对统计**。
* 合并：worker 结束后把各自 `measure.csv` 的行与 `raw_lines.log` 的逐字行并回主 run，
  再用 `-Task repair` **按测量主键去重重建**主表；`Test-RunCompleteness` 硬校验
  **无缺格、无重复**（缺格会打印出来让续跑补齐）。
* `-Task equiv`：同一批格子串行跑一遍、`-Workers K` 跑一遍，除时间戳/批次文件名外
  **逐字段比对**，并报加速比。

### 9.2 5v5 静态结论（明确回答；**未改动 `对局.gd`**）

**问：传 5 个 hero_id 会丢人还是崩？** → **丢人，不崩。**

| 事实 | 依据 |
|---|---|
| 出生格各只有 **3** 个 | `对局.gd:26-27` `P_CELLS`/`E_CELLS` 各 3 个 `Vector2i` |
| 只用前 3 个 hero_id | `对局.gd:304-307`：`for i in P_CELLS.size()` → `player_placement[P_CELLS[i]] = _p_deck[i]`，所以 `_p_deck[3]`/`[4]` **从未被消费** |

| 判负仍是 **3 杀** | `src/Battle.gd:188` `const LOSS_DEATH_COUNT := 3`（另有 `DEPLOY_COUNT := 3` @ `155`、`DEPLOY_COUNT_BATTLE := 3` @ `824`） |

**推论**：第 4、5 名英雄在当前 harness 里**永远不参与**，所以**无法用"用户同条件（5 人卡组 + 替补）"
在训练 harness 上跑**——那个口径要走检视器。训练继续用 **3v3 + 阵容轮换（49 英雄全覆盖）**。

**附带风险（供将来加替补时参考，本轮不动）**：双控模式下 `_is_manual_sub_faction` 对敌方也返回 true，
敌方替补**不会自动落位**；玩家侧会进 `State.SUBSTITUTING` 等 UI（`Battle.gd:1836-1838`），
headless 下没人点 → 只会撞 `READY_WALL_MS = 30000` 超时。所以要开替补，**还得在驱动侧接一个
替补决策策略**，不是填个 roster 就完事。

### 9.3 提速提案 → `RL/train/speedup_proposal.md`

**结论：动画/技能演出不是主要成本，"缩短动画"能省的 <10%。**

* 证据：`action_finished` 在 `_do_move`/`_do_attack` 的**同步尾部**发出（`Battle.gd:3256`/`3496`），
  这两个函数体内**零 `await`**（已做范围扫描）→ **驱动从不等动画**；`ACT_WALL_MS=400` 是永不触发的保护上限。
* 被 `await` 的只有 `_end_side` 里的回合末技能停顿（0.35s/单位）与换边停顿（0.8s/次），
  **已被 `Engine.time_scale = 20`（`对局.gd:295`）压成 0.0175/0.04s**，按 36 个半回合算 ≈**2s/局（<10%）**。
* 真正的成本是 **AI 搜索**，且其中有一块**与 beam 无关**：
  slow seed 的 `search_ms_max` 在 beam 1200/600/400/200 下几乎不变（39276/39125/39150/39252ms）。
* **唯一显著杠杆：`MAX_MOVE_OPTIONS` 16→8**（评分参数 + 分支因子），已列为阶段 1 头号待测项。
* 不建议为提高 `time_scale` 或删除生产动画而冒险（收益 <5%，且有"墙钟上限提前触发→不可复现"的风险）。
