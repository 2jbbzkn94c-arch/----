## 1. 今晚拿到的实测结论

### 1.1 对手侧 beam：**800 是白花算力**（已用真扫描证明）
| 对手 beam | 局数 | 噩梦(候选)胜率 |
|---|---|---|
| 100 | 32 | 53.1% |
| 200 | 32 | 56.2% |
| 400 | 32 | 53.1% |
| 800（旧默认） | 32 | 56.2% |

**注入口生效的硬证据**（上次翻车就是因为没做这个自检）：`opp_800` 与 `opp_100` 有 **14/32 局**结果不同、与 200/400 各 **10/32 局**不同；而**打补丁前**跑的那轮 `opp_800` 与这轮 `opp_800` 在 28 个重合场次上 **28/28 完全一致** → 说明"显式 800 = 默认行为"，补丁只让低值生效。

**推论**：① 训练可以拿低 beam 当对手，省钱且无可测偏差；② 生产困难档降到 200 测不出强度损失，AI 出手会快几倍（**要改 `src/BattleAI.gd` 的 `_beam()` 难度表，需你批准**）；③ **对手被削到 100，候选也没多赢** → 候选的胜率不是被对手强度卡住的，训练有实打实空间。

### 1.2 候选侧 beam：200~1200 无可分辨差别

## 3. 计划改了什么（已写进 `train_spec.json` 的 `phases_v2_design`）

你今天凌晨的思路我采纳并落成了规格：
1. **对手改用混合池**：70% 自对弈（对手 = 上一代检查点 / θ+小扰动）+ 30% 固定困难档（beam 100）。理由：固定对手的"幻觉"会被学成捷径，且一旦压制它就信号饱和；自对弈永远 ~50%，每局都有信息。**需要 `RlTrain.ps1` 支持"按 cell 选对手"**（`opp=cand` 已在 `对局.gd` 里支持，不用动冻结文件）。
2. **搜索方式**：先 P1 筛选出 3~6 个真杠杆（判据：配对 Δpts 的 95% CI 不含 0），再**坐标上升**（每轮只动 1~2 个参数、96 局、显著才接受）。英雄系数**分组调**，不 49 个一起。
3. **主指标改用场均分差 Δpts**（信息量约是胜负的 3~5 倍），胜率只作展示。
4. **验收换面板**：困难档 800 + 困难档 100 + **上一代的自己** + 镜像自对弈；判据 = 对前两者 Wilson 下界 > 0.5 **且对自己旧版本 > 0.5**（最后这条最防自欺）。
5. **第 0 步先修信号**：把"伤害多算 / 反击判断"那一族清掉再练权重，否则是在歪尺子上优化。

## 6. 夜间实况（01:15 更新，含两次失败的真实原因）

**低 beam（50/100/200/400）两轮都失败了 —— 两次都是"我自己的两个后台任务撞车"，不是机器的问题：**
- 第一轮（22:49 起，6 并发）：我以为它已经退出，实际它还挂在"等机器空"的循环里；与此同时我又发了第二轮 → **两个 run 同时写同一批 `results\w1..w6`**，单 cell 墙钟被拖到 558 秒，一个批次撞 900 秒超时 → 拒绝合并。
- 第二轮（00:15 起，4 并发）：启动时想清空 worker 目录，但**文件正被第一轮的 worker 占用**（stderr 明明白白：`b_beam_100_s10003_fp.out 正由另一进程使用`），随后 worker 又撞上 `w2\measure.csv 正由另一进程使用` → 再次拒绝合并。
- **结论：这轮没有低 beam（50/100）结果。** 已有的结论仍然成立：候选侧 200 / 400 / 600 / 1200 无可分辨差别（50.0 / 56.2 / 53.6 / 50.0）。50 和 100 待补（不急，因为趋势已经平了）。

## 7. 【重要】并行 worker 静默丢 cell 的 bug（02:25 发现，已派人修）

**现象**：P1（21 臂 × 16 cell = 336 cell = 672 局）跑完报 `exit=0 / all workers done`，但
- 每个 worker **分配 56 cell，实际只完成 36~40**（w1=40 w2=39 w3=39 w4=36 w5=40 w6=37 → 共 231，少 105）
- `measure.csv` 只有 **462 行**（应 672）
- **最后 6 个配置（`p1_buff_lo/hi`、`p1_jitter_hi`、`p1_hv_core_lo/hi`、`p1_hv_all1`）0 行，`raw_lines.log` 里连批次头都没有**（压根没启动）
- `p1_obst_hi` 只 16/32 行、`p1_obst_lo` 30/32
- **全程零报错**：没有 worker FAILED、没有 `produced 0 game rows`、没有 `[par] !!`

丢的正好是 **cell 列表尾部**（cell 按 config 分组、再 round-robin 分发，所以尾部截断表现为"最后几个配置整体消失"）。这也解释了更早的 `pbeam`（116/128）与 `oppbeam`（124/128）——同一件事，我当时误判为偶发丢行。

**处置**：① 立刻停掉复制块（跑的同一路径，纯浪费）；② 派写手定位 + 修，并要求加**两条硬闸门**（worker 开工前断言 cell 数；父进程合并前断言"完成 cell == 计划 cell"且"行数 == 计划局数"，不等就 throw 拒绝合并）；③ 自证规模 = 8 配置 × 16 cell = 256 局，要求 256 行、每配置 32 行、"分配=完成"全部对上；④ **修好前不重跑 P1**。
