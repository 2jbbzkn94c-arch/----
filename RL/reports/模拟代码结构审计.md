## 3. "看起来像问题、实际是合法"的典型例子（避免重复怀疑）

这些形态在扫描里都会命中，但逐处核对后都**不是**事故残留：

1. **同一循环体被多趟复用**（最容易被误报的一类）
   - `_sim_on_move` 里 `for i in sim.units.size():` + `var t: SimUnit = sim.units[i]` 在
     1486 / 1501 / 1505 / 1510 / 1517 / 1569 等处反复出现。每个循环的**守卫条件与动作都不同**
     （hero_17 相邻伤害 / hero_31 先打敌人 / hero_31 再打队友 / hero_26 冰冻 / hero_06 治疗 / hero_38 电击），
     是"按英雄分派各自的移动后技"，**不是重复插入**。
   - `_evaluate` 里 2162 / 2212 / 2222 / 2227 / 2240 / 2262 / 2276 / 2285 / 2292 / 2298 共 10 趟遍历
     同一个 `sim.units`，每趟算**不同的评分项**（价值/集火凸性/被打次数/残血/吃矿/踩雷/搏命/骗反击/德鲁伊光环）。
     这是刻意的"逐项累加"写法，且注释逐段解释了为何不能合并。

2. **if/else 两侧写同一组字典**（903/908 那类）
   - `_move_cells` 的渗透 vs 普通分支：`stop` 两侧都写、`blockers` 只有一侧写。
     **语义相反**，不是复制粘贴。

3. **"先收集集合、再按集合过滤"的双趟写法**（842/851 那类）
   - `_actions_for` 的远程不贴脸闸门：第一趟建 `safe_targets`，第二趟过滤 `kept2`。
     GDScript 里不能一边删一边遍历，必须两趟。

4. **"同一规则分三层条件逐条对齐真实脚本"**（1475/1479/1484 那类）
   - 风语者三段判定（`other_ws` → 发放者是否受控 → `giver_ok`）对应真实脚本三条规则，
     注释 1443-1449 明确写了为什么要分开判。

5. **命中存活 / 命中致死两个真实分支各写一段**（1317/1326 那类）
   - 白游侠散射在"目标被击杀"时走真实的 `on_attack_dead` 分支，规则不同（目标本体不再冰冻但相邻照散射），
     所以两段注释、两段处理都是必需的。

6. **`u.possessed_by` 看着像"只写不读"，其实有读点**
   - 写：436、1385；**读：1791**（`m.possessed_by == caster.sim_index`，宿魂镜像判定）。
     字段扫描工具若只匹配 `\.name =` 会把它误报成只写。

7. **`_print_decision` 里的 `new_d` / `old_d` / `nearest` 等"算完好像没用"**
   - 实际都在 611-619 行被读（`if old_d >= 0 and new_d >= 0:` / `new_d < old_d` / 打印）。**有读点**。

8. **`_buff_value(_sim, ...)` 参数带下划线**
   - 下划线前缀在 GDScript 里就是"有意不用"，不是漏用。这是全文件**唯一**的未使用参数。

9. **`Sim.graves[best] = true`（1947）与 `Sim.graves[cell] = { "hero":…, "fn":… }`（1669/1909）值类型不一致**
   - 看起来像"错位"，但 `graves` 的**所有消费者只用 `.has()` / `.keys()`**
     （886/900/905/983/1053/1815/1925/1944，以及 harness 的 `_terrain_diffs` 只比较键集合），
     从不读 value。所以**行为等价**，不是缺陷。若将来有人开始读 value，这里会变成坑，值得记一笔。
