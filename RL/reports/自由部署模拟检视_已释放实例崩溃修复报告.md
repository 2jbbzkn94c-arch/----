## 3. 根因核对（含一处需要更正的细节）

### 3.1 崩溃点
`src/BattleSnapshot.gd:37` `var list: Array = pool if pool.size() > 0 else battle.units`；`:45` `var u: Unit = list[i]` —— **带类型标注的赋值**。pool 里一旦有已释放实例就报 `Trying to assign invalid previously freed instance`，并且函数中断、返回 `{}`。

### 3.2 生产侧不撞（已核对）
`src/Battle.gd:5022` 只在回合开始 `var refs: Array = units.duplicate()`（这份给回放用），`:5023` 调 `BattleSnapshot.collect(self)` —— **不带 pool**，落回实时 `battle.units`，阵亡者早已 erase，所以生产不会踩到。检视器则把回合开始冻结的 `_desc_keys` 当 pool 一路传下去（原 315 / 324 行），这是唯一踩坑的地方。

### 3.3 阵亡时序（**更正一处描述**）
不是"先 `units.erase` 再淡出"，实际顺序是：

1. `Unit.die()`（`src/Unit.gd:634-642`）：`alive = false` → 起一个 **0.3s 淡出 tween** → `tween_callback` 里才 `died.emit(self)`；
2. `Battle._on_unit_died`（由 `died` 触发）才做：立墓碑（`Battle.gd:4273`）、`units.erase(u)`（`:4278`）、`u.call_deferred("queue_free")`（`:4288`）、替补判定。

所以单位在"阵亡 → 结算"这 0.3s 里**同时留在 `units` 与 `_desc_keys` 里**（`Battle._drain_pending_deaths()`（`Battle.gd:5098`）正是遍历 `units` 找 `not u.alive` 等它结算），结算之后才 erase+queue_free，再往后一帧才真正释放。这正好对上两个崩溃窗口：

- `_step:315`：停顿 `TELL_GAP/HERO_GAP=0.7s`、`STEP_GAP=0.25s` 之后的第一件事就是快照 —— 0.3s 淡出刚好够在这段停顿里走完；实测崩溃栈 `_step:315 ← _sleep:1015` 就是这个窗口（用户实机那次也是 315）。
- `_step:324`：某一招动画（0.2~0.6s）期间，名单里**别人**的淡出结算完成并被释放，出招后快照再碰它。

### 3.4 触发链（与用户描述一致）
回合开始冻结 `_desc_keys` → 回合中某单位延迟阵亡（日志里 `[替补] 我方伐木工 延迟阵亡`）→ 淡出结束、erased + freed → 之后任一步的快照仍拿冻结名单当 pool → 崩。

### 3.5 方案 A 的前提核对（我自己验的）
`Battle.units` 全生命周期**只有 append 与 erase，从不重排**（`src/Battle.gd` 里 `units.append`:1677 增援 / 4108 召唤 / 5002 替补落位；`units.erase`:4278 阵亡；没有 `insert`/`sort`/`shuffle`/`remove_at`）。而中途落位的替补（`_plan_enemy_late_sub`，`:4336`）与召唤物只会 append 到**末尾**，并且它们本来就不在这份 plan 的下标空间里（plan 是按回合开始的名单编的）。

⇒ "回合开始的名单去掉已离场者"与 `units` 里的在场顺序**逐一对应**，按下标映射换算不会张冠李戴。前提成立，因此用方案 A，不需要方案 B。

## 4. 改了哪 8 处、为什么这么改

核心原则：**执行侧继续用"回合开始的原下标"，快照/模拟/对拍侧全部改用"本步活单位列表（view）的下标"，两边各自自洽。**

1. **新增 `_step_view()`**（`:308-339`）：把 `_desc_keys` 过滤成 `{ units, src }` —— `units[k]` 是"还活着、能对拍"的单位，`src[k]` 是它在 `_desc_keys` 里的**原下标**。
   - 过滤条件：`is_instance_valid(u)`（**先验有效性再取成员**，绝不用带类型标注的赋值接可能已释放的实例）+ `u.alive`。
   - 保留 `hp <= 0 但 alive == true`（延迟阵亡结算中，见 §3.3）——它还在 `units` 里，照旧进名单，由 `_collect_units` 的 `zero` 表按"出招前就 0 血"跳过比对。
2. **重写 `_step()`**（`:342-398`）：
   - view 必须取在 **`_sleep` 之后、快照之前**（这是 315 崩溃的窗口）；这一段到出招前快照之间没有 `await`，所以中途不会再有单位离场；
   - `idx = vsrc.find(_cur_idx)`；**找不到就 `return "changed"`**，走 `_drive_enemy_turn()` 里既有的"单位集合已变化…本回合剩余计划作废"路径（不静默跳过、也不打错人）；
   - 计划里的 `atk` 是原下标，喂模拟前换算成 view 下标（`a_pred`）；目标已离场则 `_predict` 报 **NOPRED 并写明原因**，不硬凑"这招没打人"的假 MATCH；
   - 出招前 `SNAP.collect(_battle, view)` / `_collect_units(view)` / `_predict(view, before, idx, a_pred, why)`；
   - **出招后 `_collect_units(view)` 重新过滤后当 pool**（这一招里阵亡的人可能刚被释放，直接复用 view 会重演 324 崩溃）；`keys/src/zero` 三者同源同基准，"单位数 预测N→实际M（出招后有单位离场/下标位移）"这条判定**原样保留**；
   - `res["atk_idx"]` 换算到 view 基准后再交给 `_compare`。
3. **`_predict(..., why := "")`**（`:401-411`）：`why` 非空直接返回 `{ok:false, why}` → NOPRED。
4. **`_compare(pred, after, vidx, view, a, res)`**（`:467-476`）：参数改名 + 文档；`rec["idx"]` 仍记 `_cur_idx`（**原下标**）——`_tally` 的去重键按它算，若改成 view 下标，回合中途有人阵亡时下标会整体前移，去重键可能撞车而漏计招数。
5. `_compare` 内 `_hero_of(descs,i)` → `_hero_of(view,i)`（`:511`）。
6. `_compare` 内两处 `i == idx` → `i == vidx`（`:542`、`:545`）；反击旗标那处补注释说明 `atk_idx` 已同基准（`:552`）。
7. **`_call_action()` 取攻击目标**（`:629-641`）：原来 `var t: Unit = refs[ti] …` 是**带类型标注的赋值**，`refs = _desc_keys` 是冻结名单，目标已被释放时**同一个错误**会在这里炸（而且它在一次 `await`（移动动画）之后才取，是真能碰上的）。改成无类型取值 + `is_instance_valid` / `is Unit` 逐层验；验不过就走既有的"被真实规则拦下"分支（如实打印、不崩、不伪造出手）。执行侧仍用原下标，`out["atk_idx"]` 也仍是原下标（由 `_step` 换算）。
8. `_call_action` 文档注释补上 `atk_idx` 的口径（原下标）。

**没有做的事（按要求）**：没删/弱化任何对拍字段与判定（墓碑/障碍/炸弹/金矿/道具/单位数/行动旗标/反击旗标全部保留）；没 catch 异常当没发生；没把 `SNAP.collect` 的 pool 去掉；没动 `src/BattleSnapshot.gd:45` 那个既有脆弱点。

### 5.5 逐条 DIFF 判定（不靠放宽判定减少）

**A. `墓碑` 类 → 判定：采样时机差（不是规则缺口，也不是本次改动引入）**

依据（代码 + 日志两路）：

- 真实侧：`Unit.die()` 先 `alive=false` 再 **0.3s 淡出**，`died` 之后 `Battle._on_unit_died` 才立碑（`src/Unit.gd:634-642`、`src/Battle.gd:4273`）→ 墓碑**滞后 0.3s**出现。
- 模拟侧：`AI_Battle._sim_kill()` 击杀时**立即** `sim.graves[t.cell] = …`（`RL/ai/AI_Battle.gd:1299-1308`）。
