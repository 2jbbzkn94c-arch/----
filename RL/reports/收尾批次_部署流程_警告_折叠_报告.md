## 00. 本轮补完：旗标行 / 一致性定性（复核绝对状态）/ 场外变化"不可比"

### 00.1 旗标行（已做，属对拍块内容，留在控制台）
格式：`  旗标：<单位> 已移动,已攻击 | <单位> 已反击 | …`，沿用字段级原名（`已移动/已攻击/已反击`）。
限制按裁决执行：
- **只有"本招出手的单位"才比较预测/实际旗标差异**。原因写进代码注释：预测侧的 sim 是"本招之前"重建的，
  其它单位的 moved/attacked 天然是 false，拿去比真实侧（已累积整回合动作）永远全是"预测否 / 实际是"。
  这与字段级 `_compare` 口径一致（它也只比 `i == vidx` 的旗标）。
- 非出手单位**只列它实际已做过的动作**，不做预测/实际对比。
- 出手单位按 **view 下标**（`rec["idx"]`）判定，不按名字（同名英雄如两个烛火会撞车）。
- **某招完全没有旗标差异就不打这一行**。
- 顺带修：`_snap_of` 原来没带 `moved/attacked/counter_used`（只有 `_snap_sim` 带）→ 旗标行取不到值，实测是空的；已补齐。

样例（真实输出）：
```
  旗标：雪拳(hero_26)#5 已移动,已攻击 | 伐木工(hero_01)#5 已反击
  旗标：医护兵(hero_06)#2 已移动,已攻击 | 烛火(hero_17)#3 已移动
```

### 00.2 一致性定性（按裁决：就地复核绝对状态）
`_classify_process_diffs()` + `_abs_state_differs()`：对每条"可读层有差异、字段层为空"的项，
按条目文本解析出**类别（障碍/炸弹/墓碑/金矿/道具）或单位名**，再比**绝对状态**
（`sim.<dict>` vs `after[<key>]`；`SimUnit` 字段 vs 真实 `Unit.has_status`）：
- 绝对状态**不同** → 真缺口 → 写 `[告警] 字段层漏报：…` 进运行时文件，判定保持 `DIFF`；
- 绝对状态**相同** → 纯过程/时序差异 → 判定写 `MATCH（绝对状态一致；仅过程差异：…）`，**不计入 DIFF**。

过程中修掉我自己的三个口径错误（都踩过）：
- 原来按"变化行数"统计可读层差异 → MATCH 的块也被误报（**18 条假告警**）；
- 改成"两侧不一致处数"后仍**按行号硬比** → 两侧条数不同就整体错位；再改成**与顺序无关**；
- 把"`无变化`"这个**标记行**当成了差异项（导致合法 DIFF 被误判成"字段层漏报"）→ 已跳过。

### 00.3 场外变化 → 判"不可比"（本轮新增）

**给用户的一句话**：对拍块里只要出现 `判定 不可比（本招期间有场外变化：…）`，**这一招可以直接跳过**——
它既不算 MATCH 也不算 DIFF。原因：这一招的"出招前快照"和"出招后快照"之间，盘面被**本招动作之外**的
东西动过了（替补落位 / 延迟生效的效果等），预测与实际已经**不在同一个前提**上，比了没有意义。
`SUMMARY` 行尾的 `SPAN=` 就是这个计数（`SPAN=0` 表示本次运行一招都没撞到场外变化）。

**触发条件（唯一入口）**：`_step()` 里"出招前快照 `pre.real`"与"出招后快照 `post.real`"之间，
被 `_turn_span_reasons()` 机检出下列三类证据中的任意一条。**没有证据就不标**——绝不做成"凡有差异就甩锅场外"。

`_turn_span_reasons()` 机读检测三类**非本招动作造成**的变化，命中即标"不可比"（不计入 DIFF、单独计 `SPAN`、内容照旧展示）：
1. **单位集合变化**：`pre.real` 与 `post.real` 的单位 key 集合求差 → "有新单位登场（替补/召唤）" / "有单位离场/被撤下"；
2. **墓碑格上多了人**：`pre.real.grave` 某格在 post 里被新单位占据 → "替补在墓碑 X 处落位"；
3. **延迟效果落地痕迹**：某单位在**实际侧凭空**获得[圣盾]而预测侧没有，**且本招没有"道具被拾取"** →
   "延迟效果落地（非本招拾取）"。（模拟侧 `_sim_*` 给盾是同步的，所以"只在真实侧凭空多出盾"就是场外来源的指纹。）
**没有做成"有差异就甩锅场外"**：只有检出上述证据才标不可比。
实测：两个种子 20 招里 **`SPAN=0`**（本轮没撞到"替补在两招之间落位/延迟给盾"的样本）→ 该机制**已实现但尚未被真实样本触发**。

## 0. 【已解决】部署流程最终修好了 —— 真凶是我自己 `_ready()` 里的一个 bug

**根因**：`_apply_emode(...)` / `_apply_mode(...)` 被我放在 **`if _selftest:` 里面**，
于是 `--test-picks --pai 1 --ai 1` 这种**非自检**的取证运行**根本没应用档位**，
`_mode/_emode` 一直是 0（手动）→ `_deployment_tick()` 判 `ai_side=false` 直接 return，
部署自然停在第 1 手。查证链路：逐帧打 `st=4 side=0 p=0 e=1` → 打"即将调用 tick"确认确实调用了 →
在 tick 第一行打 `_mode/_emode` 看到**都是 0** → 再打参数解析结果 `st_pai=1 st_ai=1`（解析没问题）
→ 定位到"解析对了但没应用"。
**修法**：把两个 `_apply_*` 移到 `if _selftest:` **之外**（无参数时默认值都是 AI_MANUAL，
所以固定 3v3 / 自检路径行为不变，基线已复核）。

**逐手部署日志（`--test-picks --pai 1 --ai 1`，双方都 AI）**：

**落位机制（按 HUD 权威路径复刻，不是从 Battle 里挑函数猜）**：
- `src/HUD.gd:628-642`：点英雄卡 → `state==DEPLOY` 时 `battle._on_deploy_pick(hid)`（写入 `_pending_deploy`、`state=PLACE_DEPLOY`）；`PLACE_DEPLOY` 时再点卡片是"反悔/切换"（`_on_deploy_pick_again`）。
- `src/Battle.gd:2166-2173`：点棋盘格 → `state==PLACE_DEPLOY` 时**看 `_pending_enemy_deploy` 是否为空**决定放哪一方（空 → `_try_place_deploy`，非空 → `_try_place_enemy_deploy`），且落格必须是"该方出生格且空格"（`_in_spawn_cell` + `occupancy` 双重校验，不合格**静默 return**）。
- 所以 `_deployment_tick()` 对 AI 那一边做的就是"替他点那一下棋盘格"：`_free_spawn_cell(fn)` 找空格 → 按 pending 情况调对应落位 API；并**专门处理"敌方 pending 还挂着、轮次已回到我方"**的情况（先把那一手落完），否则 `state` 永远出不去 `PLACE_DEPLOY`。

**用户视角的完整流程（F6 → 开打，一步一句）**：
1. F6 进检视器 → 显示**英雄池选人界面**（`QuickTest`，5 列蜂窝卡，可切"编辑我方 / 编辑敌方"）。
2. 给自己勾人（≥3、≤8；**前 3 名 = 首发候选**），切到敌方再勾一遍（不勾则按 QuickTest 口径随机补 8 名）。
3. 点「开始对局」→ **不换场景**，检视器内部建战场，**进入 Battle 自己的轮流部署流程**。
4. 部署阶段：**档位=AI 的那一边由工具一手一手自动上人**（上一个、等一手、再上一个，走的正是 HUD 那两步）；**档位=手动的那一边由玩家自己在游戏内部署界面点选**（英雄卡 → 出生格），工具不插手、也不替它结束。
5. 双方各上满 3 人 → Battle 自己 `_begin_after_deploy()` → `_start_match()` → **正式开打**，逐招对拍照常。
6. 对局中点 HUD「返回选人」→ 回到检视器的英雄池界面（保留上次勾选）。

**要转告用户**：英雄池只负责**卡组**；"谁上阵、放哪格"由 **Battle 的部署界面**负责——
所以会出现部署这一步，不再是"前 3 名直接落在固定格上"。

## 1. 【已修并验证】"选了英雄进去却是默认阵容"

**根因（比你标的两行更严重一层）**：`_on_quicktest_start()` 先写好勾选，随后调的 `_setup()`

  实例化战场/`add_child`/`_hook_hud_back_button()`）照常。
- `keep_picks = false`：**行为一字未变**（固定 3v3 / `--selftest` / `--fixed3v3`）。
- 那段写错的注释（"那条路径不经过本函数"）已改成事实描述。

## 2. 【部分完成 / 有阻塞】英雄池只定卡组 → Battle 自己的轮流部署

### 已实现的骨架
- `_on_quicktest_start()` 不再写 `placement`（写了就跳过部署界面），只写 **卡组**（前 3 名是首发候选）。
- 部署由 **Battle 自己的流程**跑：`_run()` 里先走"部署阶段循环"（判据用 Battle 的
  `State.DEPLOY` / `PLACE_DEPLOY`，**没用** `PLAYER_INPUT` 去猜），部署完成后 `_deployed = true` 再进对拍主循环。
- `_deployment_tick()`：**只驱动"档位=AI"的那些边**，一手一手地上人：
  - 选谁 → 复用生产 `_enemy_deploy()` 的评估口径（首发 `_hero_strength`，之后 `_deploy_candidate_value` 协同打分，
    并同样跳过带 `<替补>` 标签的英雄）——**没有**自己写"按勾选顺序取前 3"；
  - 落哪格 → 生产自己的 `_free_spawn_cell(fn)`；
  - 落位 → 游戏自己的部署 API `_on_deploy_pick()` + `_try_place_deploy()`（选人→落位两步）。
  - 敌方轮且敌方=AI 时**不重复驱动**（生产 `_deploy_after_pick()` 自己会 `_enemy_deploy.call_deferred()`）。
- `_assert_deploy_done()`：部署结束断言"双方各 3 人上阵，且都来自各自卡组"。
- 手动那一边**完全不插手**（`_deployment_tick` 直接返回），玩家点游戏自己的部署界面。

### ⚠️ 阻塞（未解决，需要继续排查）

**下一步建议**：在 `_deployment_tick()` 的 PLACE_DEPLOY 分支里逐项打印
`state / _deploy_side / _pending_deploy / _pending_enemy_deploy / _free_spawn_cell(fn) / occupancy`
六个值各一帧，先确认到底是"没空格"还是"pending 为空"，再决定是补落位还是补选人。

## 4. 【已完成】折叠后矩形仍挡棋盘

**根因**：`_on_fold()` 只藏了 `_scroll`，**没缩 `_panel`**；而 `_panel`（固定 292×760）与
`bg`（PanelContainer + FULL_RECT）默认 `mouse_filter = STOP`，折叠后仍占着那整块矩形 →
棋盘上这片区域的点击被吃掉（用户说的"背景挡住"其实是**看不见的挡板**）。

**修法**：折叠时把 `_panel.size` 缩到"只剩标题行"，展开时还原（成员 `_panel_expanded_size` 记住展开尺寸）。
**踩到的坑（已解决）**：不能用 `_panel.get_combined_minimum_size().y`——`_scroll` 一隐藏，
容器的合并最小高度会变成 **0**，面板会缩成 `292×0`（标题行跟着不可见）。
实测值：折叠态 `combined_min=(292, 0)`、`head` 高 37 → 改为"取 head 自身高度 + 容器 separation，再兜 37"。

**机读证据（进运行时文件）**：
```
fold-check 1/2 折叠态 面板矩形=(6,6,292,37) 标题行=(6,6,292,37) 高差=0.0 面板底+20 是否仍被面板覆盖=false
fold-check 2/2 展开态 面板矩形=(6,6,292,760)（已还原，应远高于标题行 37）
fold-check 恢复尺寸=760（折叠前记住的展开高度=760）
fold-check VERDICT=PASS（…折叠后面板缩到只剩标题行、不再覆盖棋盘；展开后尺寸还原）
```
改前：折叠后仍是 `292×760`；改后：`292×37`（= 标题行高度，高差 0.0），棋盘不再被覆盖。
`_fold_assert()` 已加：折叠态"面板高≈标题行高"+"面板底+20 的点不再被覆盖"、展开态"高度还原"，
且缩/还原后都 `await process_frame` 再量（防"全 0 矩形"假绿）。

### 关于"字段级 buff 到底有没有参与比较"（代码路径）
**有参与**。`_compare()` 末尾五行地形比对里就有：
```gdscript
rec["diffs"].append_array(_terrain_diffs("道具", sim.buff_cells, after.get("buff", {}), false))
```
（同段还有 障碍耐久/炸弹/墓碑/金矿）。`_terrain_diffs(..., by_val=false)` 比的是"某格在不在"：
`(pv == null) != (rv == null)` 才报差异。两侧数据源分别是模拟 `Sim.buff_cells` 与
真实快照 `BattleSnapshot.collect()` 的 `buff`（它在 `BattleSnapshot.gd:51-58` 把 `buff_items` 按 `gold`/其它拆开）。
所以口径是一致的——**当初那条"字段级为空"我现在判断是"上一轮那个 `_apply` 前/后别名 bug + 快照取错时机"的副作用**
（字段级用的是 `after` 快照、而可读层当时用的是错时机取的快照，两层不同源）。
修好快照时机（第 6 节）后，`--selftest 20` 里 terrain 类 DIFF 与字段级已能一一对应（`diffs=` 非 `-`）。
**若用户在最新版里仍看到反向矛盾，双向 `[告警]` 会在运行时文件里直接打出来**，可直接抓。

## 6. 【早前完成，未回退】快照时机与判定自洽

- `_predict()` 内、`_apply` **之前**存 `sim_pre`（`_apply` 是原地修改同一对象，
  所以调用方事后取 `pred["sim"]` 永远是"预测后"状态 → 预测侧恒"无变化"）。
- 判定**由块内两侧展示直接推出**：两侧逐条相同判 `MATCH（两侧项一致）`；有一条不同判 `DIFF` 并给出第一处不同的
  "预测 X / 实际 Y"，字段级 `diffs=[...]` 另起一行。
- 快照单位键 = **view 下标字符串**（`_ukey(k)`）；两侧都用同一 `view` 生成，**同源同序**。
  对象键不可靠的实证：`_by_key()` 曾只剩一项 → 逐单位对比恒"无变化"。
- 快照无效时**拒绝列项**（打印"快照无效"），不印 `0→3` 这类幻影。
- `String(<Variant>)` 全部改 `"%s" % v`（本项目 `String(<Object>)` 会报
  `Nonexistent 'String' constructor` 并返回 null）。
