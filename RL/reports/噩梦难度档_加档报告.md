  这个函数在**主线程**跑，所以就算难度=3 在这里读一次权重文件也是安全的（每局最多几十次，可忽略）。
- 第 5151 行：**必要改动** —— `_enemy_ai_worker(ai: BattleAI, ...)` → **`_enemy_ai_worker(ai: RefCounted, ...)`**；
  第 5152 行 `var sim := ...` → `var sim = ...`（去掉类型推断，因为 `ai` 不再有具体脚本类型）。

  > **理由**：GDScript 的形参类型注解是按**脚本资源**比对的，不是按"有相同的成员所以结构兼容"。
  > 噩梦档传进线程的是 `res://RL/ai/AI_Battle.gd` 的实例，它是**另一份脚本**（虽然也 `extends RefCounted`），
  > 因此形参写 `BattleAI` 时 `Thread.start()` 的实参转换直接失败，实测报错：
  > `Could not call function 'Node2D(Battle)::_enemy_ai_worker' to start thread 32:
  > 'Node2D::_enemy_ai_worker': Cannot convert argument 1 from Object to Object.`
  > → 线程根本没起来，敌方回合**静默空转**（不报崩、不出手，最难查的那种）。
  > 改用 `RefCounted` 后：候选与生产 AI **都**满足该类型，生产路径的类型检查结果不变（§5.5 有零影响推理）。
  > `var sim :=` 必须同时改成 `var sim =`：从"无具体脚本类型的变量"取返回值无法类型推断，
  > 否则报 `Parse Error: Cannot infer the type of "sim" variable`。
  > 同一陷阱在 §1.2(b)（工厂）与 §1.2(d)（`_plan_enemy_late_sub`）也适用：**凡是从"按路径 load 出来的 AI"取返回值处，
  > 都要写 `var x = ...`，且接收变量绝不能标注成 `BattleAI`。**
- 线程体内**没有**任何文件 IO / 场景访问，仍然只有 `build_state` / `search`。

### 1.6 噩梦档的搜索宽度：`BEAM=1200` 与困难档默认 800 的关系

| | 波束宽度（`BEAM` / `w_beam`） | 抖动（`JITTER`） | 来源 |
|---|---|---|---|
| 简单（0） | 50 | `randf_range(-8.0, 8.0)` | `src/BattleAI.gd:_beam()/_jitter()` 硬编码 |
| 普通（1） | 300 | `randf_range(-1.5, 1.5)` | 同上 |
| 困难（2） | **800** | **0.0** | 同上（= `RL/ai/AI_Battle.gd` 的默认值） |
| **噩梦（3）** | **1200** | **0.0** | **`RL/weights/噩梦.json` 的 `BEAM` / `JITTER`**（可改，无需改代码） |

- 候选的 `_beam()` / `_jitter()` 在 `difficulty >= 2` 时返回 `w_beam` / `w_jitter`（`RL/ai/AI_Battle.gd:526-539`），
  所以难度 3 天然落在 `>= 2` 分支 → 取注入值：**噩梦 beam = 1200，比困难档宽 1.5 倍**。
- 代价（实测）：同一个 3v3 开局局面，候选在难度 3 下 `build_state + search` **3149 ms**（复跑一次 3725 ms，
  同一台机器有波动）。困难档用的是同一个评分函数 + 更小的 beam，所以**噩梦比困难慢一点、强一点**——
  慢在搜索宽度，强在两处：模拟更准（几十处 `【RL 修正】`）+ 这个备选空间更大。
- 兜底：候选仍有 `time_budget_ms = 10000` 的 deadline，搜不完会自动收窄，不会因为 1200 就无限卡住。
  想更快/更省就调小 `噩梦.json` 的 `BEAM`（例如 800 = 与困难同宽，变成"只有模拟更准"的噩梦）。

## 4. 【重点】以后怎么把训练好的权重装进噩梦档

**一句话：只替换 `RL/weights/噩梦.json` 里的数值，不需要改任何一行代码** —— 训练完立刻能玩到"真噩梦"。

### 4.1 操作步骤

1. 打开 `RL/weights/噩梦.json`。
2. **只改那 12 个业务键的数值**（`KILL_BONUS` / `FOCUS_FIRE_WEIGHT` / `GOLD_TAKE_VALUE` / `GOLD_TAKE_VALUE_LOW` /
   `GOLD_LOW_ATK` / `BUFF_TAKE_WEIGHT` / `THREAT_MOVE_DISCOUNT` / `OBSTACLE_DETOUR_WEIGHT` /
   `ENGAGE_PULL_PER_CELL` / `MAX_MOVE_OPTIONS` / `BEAM` / `JITTER`）。
   `_` 开头的说明字段随便改，它们**不参与注入**。
3. 保存。**下一局**开打即生效（游戏在"敌方回合开始、建 AI 实例"时读这个文件），**不必重启游戏**，
   正在打的那一局也不受影响。
4. （可选，强烈建议）设 `ZB_NIGHTMARE_DEBUG=1` 启动，看敌回合那一行日志：
   `注入键数=17 | BEAM=… | JITTER=…` —— 确认文件真的被读了、数值就是你写的那套。

### 4.2 三条必须知道的边界

1. **键名拼错不会报错，只会静默不生效**（候选 `set_weights()` 的 `_` 分支忽略未知键）。
   所以改完建议跑一次 §5.4 的探测脚本，或至少核对 §5.4 列出的 12 个键名。
   另外**值必须是数字**：写成字符串（`"40"` 而不是 `40`）会被 `typeof` 检查跳过，同样静默失效。
2. **不需要动 `src/`**：权重是"数据注入"，代码只看文件路径（`src/Battle.gd:168` 的 `AI_NIGHTMARE_WEIGHTS_PATH`）。
   只有当你想启用**英雄特化权重**（`set_hero_weights()`，形如 `{"hero_42": {"GOLD_TAKE_VALUE": 40.0}}`）时，
   才需要改 `src/Battle.gd` 在工厂里多调一次——**这一版刻意没做**，因为本次要求改动最小。
3. **坏文件不会崩**：删掉文件 / JSON 语法错误 / 顶层不是字典 → 只打一行 `push_warning`，本局退回候选默认权重
   （= 生产困难档口径），游戏照常打。所以"边训练边玩"是安全的，不用怕把游戏搞崩。

### 4.3 想调"噩梦的手感"也可以只改这里

- 嫌慢 → 调小 `BEAM`（800 = 与困难档同宽，变成"只有模拟更准"的噩梦；再往下降更快）。
- 嫌不可复现 / 想加随机性 → 调大 `JITTER`（`0.0` = 纯最优可复现）。
- 想要更凶 → 调大 `KILL_BONUS`（更爱收人头）、`FOCUS_FIRE_WEIGHT`（更爱集火）、`THREAT_MOVE_DISCOUNT` 调小（更敢贴脸）。
