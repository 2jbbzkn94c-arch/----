# 6. 天梯模式（连胜挑战）

> **本文档规矩**（用户 2026-09-20 定，见 `AGENTS.md`）：新内容**先整合进已有章节/表格**，不在文末另开章节；**改引擎键/权重值/档位必须在同一次改动里同步本目录**；结尾保留版本锚点 + 计数行。
> 本文档成立于 2026-09-24（用户提需求那天）：天梯是**新模式**，此前没有任何文档讲过"游戏模式/存档"，故单独一份。

## 一、用户口径（原文照录，做的时候就按这 6 条）

1. 天梯主要为了打连胜，**对局失败即为此次天梯模式失败**
2. 可以**保存退出**；退出后再进来，载入**退出前回合开始状态**，而不是对局重新开始
3. 遇到**非正常状态退出**，依旧载入退出前回合开始状态
4. 统计数据里增加「天梯普通模式 / 天梯竞技场模式」的**最高连胜**与**当前连胜**
5. 战斗胜利后，**结算界面显示当前连胜**，然后可以点**继续挑战**
6. **难度默认为噩梦**

三个当天拍板的补充（本文档记录，避免以后反复）：

- 进入天梯时有未完成存档 ⇒ **问一句**：「继续（第 N 局 · 当前连胜 M）／ 放弃并重新开始」
- 难度**锁死噩梦**（选人页不再显示难度下拉，只显示"AI 难度：噩梦（天梯固定）"）⇒ 连胜才有可比性
- 打到一半回主菜单**不算放弃**（存档留着，下次进来继续）；只有"输了"或明确点"放弃"才结束本轮

## 二、两个变体与"和谁一样"

| 变体 | 走哪套机制 | 入口后的第一屏 |
|---|---|---|
| 天梯普通模式 | 与单机**普通模式**逐字相同（进场弹「选择卡组」→ 部署 → 打） | 选人页（标题变「天梯模式」，难度行换成固定噩梦） |
| 天梯竞技场模式 | 与单机**竞技场模式**逐字相同（进局后 2 选 1 轮流构建双方卡组） | 直接进战斗，弹竞技场选人 |

⚠️ 与单机两种模式**唯一的差别**就三条：难度锁死、每回合开始落盘、失败结束本轮。

## 三、实现（落点全在这里，改之前先读这节）

### 3.1 存档：`autoload/LadderStore.gd`（新 autoload，`project.godot` 已注册）

| 存什么 | 说明 |
|---|---|
| `[runs] normal` / `[runs] arena` | 每个变体一份 `{mode, difficulty:3, match_no:局数, player_deck:[…], in_match:本局是否已开打, enemy_deck:[…]}`；缺 = 这个变体没有进行中的天梯 |
| `[drafts] normal` / `[drafts] arena` | 每个变体一份**竞技场选人中途存档**（`Battle._arena_draft_snapshot()` 的产物：池子 + 已选 + 已送 + 轮数 + 先手）；缺 = 这个变体没有选人在途。⚠️ 只有**天梯竞技场**会写它；选完（进部署那一刻）即撤 ⇒ 之后由 `[runs].in_match` 与 `[snaps]` 接手 |
| `[snaps] normal` / `[snaps] arena` | 每个变体一份中局快照（`Battle._ladder_snapshot()` 的产物）；缺 = 这个变体当前不在对局中（= 上一局已打完） |

- 文件 = `user://ladder.cfg`；写盘 = **先写 `ladder.cfg.tmp` 再改名**（原子）⇒ 写一半被杀死也不会把存档写坏
- ⚠️ **两个变体各存各的**（用户要求「天梯普通场和竞技场状态分开」）：一边打一边另一边打都行，互不覆盖
- ⚠️ **连胜数不在这里**：唯一真源是 `autoload/Stats.gd` 的 `best_streaks` / `cur_streaks`（同样按变体分开，跟着 `user://stats.cfg` 走）。本文件只管"轮次还在不在 + 局面"
- API（`m` 省略 = 当前这局的天梯变体 `GameState.ladder_mode`；**传空又不设 `ladder_mode` 时全部 no-op**，所以生产侧必须先把 `ladder_mode` 设好）：
  `has_run(m) / match_no(m) / player_deck(m) / enemy_deck(m) / has_pending_match(m) / info(m) / mode_name(m) / mode_short(m)` · `begin(m) / begin_next_match(m) / note_match_started(pdeck, edeck, m) / note_player_deck(ids, m) / finish_run(m)` · `save_snapshot(s, m) / has_snapshot(m) / snapshot(m) / clear_snapshot(m)` · `save_draft(d, m) / has_draft(m) / draft(m) / clear_draft(m)`（**竞技场选人阶段**的中途存档，见上表 `[drafts]`）

### 3.2 快照点：**每次回合开始**（`src/Battle.gd`）

```
_begin_side(side)                       ← 回合开始
  └─ _ladder_autosave(side)             ← 【存档点】还没补位/没跳毒伤/没放回合开始技
        └─ LadderStore.save_snapshot(_ladder_snapshot(side))
  …（补位 → 猛毒跳伤 → 金矿倒计时 → 回合开始技 → 输入/等 AI）
```
- ⇒ 磁盘上永远是"**最近一次回合开始**"：正常关游戏、崩溃、强杀走的都是同一条路（用户第 2、3 条一起满足）
- 只在**单机天梯**里做事：`_ladder_active()` = `ladder_mode != "" and not is_online and LadderStore.has_run()`，其它模式第一行就返回
- 快照内容（`_ladder_snapshot()`）：单位（通用字段转储）· 棋盘实体（炸弹/障碍/道具/归属/礼物隐藏格/墓碑/金矿/附体绑定）· 账本（`player_pool/enemy_pool/*_deployed/*_roster/*_dead/_pending_*_subs/_pending_sub/_gold_tick_round/_opening_items_spawned/_first_side/_deploy_side/_deck_pick_match`）· `GameState`（双方卡组/敌方配方/回合号/行动方/arena/no_death_limit/难度）· `rng.state` · **`deploy_done` / `deploy_left`**（这一局部署完没完、部署读秒还剩多少 —— 决定续档是"接着部署"还是"回到回合开始"，见 §3.3）· **`rec`**（**2026-09-28**：到这一刻为止的录像 `{meta, frames}` ⇒ 续档接着录，整局一条完整录像，见 §三之二）
- **存档点不止"回合开始"**（2026-09-25 晚补）：部署期**每上一个人**也落一次盘（`Battle._deploy_after_pick()` 末尾那次 `_ladder_autosave()`，⚠️ 放在 `_deploy_side` 翻转**之后** ⇒ 轮次标记与双方已上阵人数同口径）+ 暂停面板「保存并退出」再补一道兜底（`HUD._on_ladder_save_quit()` 改调 `Battle._ladder_can_save()`：部署期要存、选卡组/竞技场选人在途不存、赛后不存）⇒ 部署到一半**正常退出、崩溃、强杀**都能接着这份没打完的部署回来，已上阵的人是**留着**的
- **单位字段用通用转储**（`_dump_script_vars()`）：遍历脚本自己声明的成员变量，只收 `bool/int/float/String/Vector2i/Array/Dictionary`（对象/节点引用一律跳过）⇒ 以后给 `Unit` 加字段**不用回来改这里**。英雄脚本的对象级状态也一并带上 —— 52 个英雄里只有 3 个有（**锤头鲨 `bonus` · 风语者 `_aura_given` · 负墟 `_last_frame`**），同一条规则自动覆盖

### 3.3 恢复：`_ladder_restore()`（`src/Battle.gd`）

`Battle._ready()` 的单机分支里，**排在"竞技场选人 / 选卡组 / 部署"之前**加了两路（先命中先走）：

| 条件 | 走哪 |
|---|---|
| `ladder_mode != ""` 且**有快照** | `_setup_hud(); _ladder_restore()` ⇒ 重建局面。**再分两种**（看快照的 `deploy_done`，旧档缺这个字段就按双方已上阵人数推断）：`true` ⇒ 从最近一次回合开始继续（`state=IDLE` + `_begin_side(side)`，下面这段）· `false` ⇒ **接着部署**（`_resume_deploy_phase()`：已上阵的人照原格站着、卡池/已上阵名单/读秒都接回去，退在敌方轮就 `_enemy_deploy()` 接着补） |
| `ladder_mode != ""` 且**本局已开打但没快照**（`LadderStore.has_pending_match()`：刚进部署一个人都还没上） | `_place_obstacles(); _spawn_opening_items(); _setup_hud();` 然后用本轮记下的双方卡组 `set_decks()` + `_begin_deployment()` ⇒ **直接回到部署**（用户 2026-09-24 报的那条） |
| `ladder_mode != ""` 且**竞技场选人在途**（`LadderStore.has_draft()`） | `_place_obstacles(); _spawn_opening_items(); _setup_hud();` 然后 `_resume_arena_draft()` ⇒ **接上同一批候选、同一位先手、同一批已选**（2026-09-25 用户报「选人阶段退出去，能选的人就变了」） |

## 三之二、录像回放（2026-09-27 用户要求，**与天梯共用同一套快照/恢复**）

> **每局自动录**。放在本文档是因为它复用天梯的 `_snap_take/_restore_snapshot`。

**联机也录（2026-09-28 用户问「怎么联机对战没有录像」）**：原来 `_rec_*` 全都在 `GameState.is_online` 时
直接 return（当时的理由"本端没有对端的完整流水"其实**站不住**：联机两端是逐条应用同一串指令的）。
改法四条：
① **记账挪到"应用"那一层** —— 玩家指令从 `_dispatch_player_op()`（提交处）挪进 `apply_command()`；
   替补从 `_try_place_sub()` 挪进 `_place_sub()`；撤下从 `_withdraw_unit()` 挪进 `_apply_withdraw()`
   ⇒ 单机/联机主机/联机客户端（收到广播重演）三条路都**各记一次、不重不漏**。
   回放自己也走这些函数，但那时 `_rec_on = false`（`_rec_step()` 自己挡）⇒ 不会边回放边写录像；
   敌方 AI 走 `EnemyReplay` 直接调 `_do_move/_do_attack`（不经 `apply_command`）⇒ 单机里仍只有一条 `plan`，不会翻倍。
② 去掉 `_rec_begin/_rec_frame/_rec_note_deploy*/_rec_step/_rec_finish` 的联机拦截。
③ **客户端的录像要在 `_on_net_command()` 的 `match_end` 分支里收尾**（那条路是直接 `match_result.emit()`
   的，不走 `_emit_match_result()` ⇒ 不收尾的话客户端那份永远不落盘）。
④ **视角**：`meta.rec_side` 记下"录制者是哪一方"，回放时 `_my_faction()` 用它（客户端录的那份"我方"= 红方），
   棋盘 `view_flip` 也跟着翻 —— ⚠️ 只改视角，**不动 `GameState.is_online`**（那会牵动 `for_enemy` 判定、
   把回放每步的"演完放行"弄丢）。模式名记为「**联机**」。
✅ 实测（单机回归）：走一步 + 撤一个人 ⇒ 流水 `["move","withdraw"]`、落盘正常、回放终局单位/血量指纹与录制侧逐位一致。
⚠️ **联机那一半我这边没法真机验证**（要两个实例对一局）—— 需要你开两个窗口打一局确认。

**思考时间不复现**（用户 2026-09-27：「回放的时候是会把思考时间也复制进去吗？不需要」）：段的时长从**本段第一次出手**
起算（`ReplaySession.note_step()` 收 `skip_before` = 那次 AI 搜索的开始时刻），所以 AI 想 40 秒、回放也只在那一回合
停一拍；玩家自己的长考同样不进回放。段内的招式仍按真实节奏重演（走位/出手/停顿都是当时的演出时长）。

**回合切换提示**（用户 2026-09-27：「看录像的时候，回合切换不明显，需要提示蓝方回合还是红方回合」）：
回放不走 `_begin_side()` ⇒ 每进一段由 `Battle._replay_enter_frame()` 直接喊 HUD 的
`_show_turn_banner(text, color, hold)`：文案 = **「蓝方回合（第 N 回合）」/「红方回合（第 N 回合）」**
（`_turn_banner_text(side, blue_red=true)`；**对局文案一个字不动**，那里本端就是"你/敌方"），
颜色跟阵营（蓝 `(0.45,0.7,1.0)` / 红 `(1.0,0.42,0.38)`），停留 `REPLAY_BANNER_HOLD = 1.5s`（对局是 0.9s）。
横幅在**开局、每次换段、跳段落地**三处都报一次；`GameState.round_number` 也随段同步（顶栏回合号跟着走）。

**回放里没有对局入口**（用户 2026-09-27 报「怎么录像功能可以点击下方的按钮」）：HUD 的
`_refresh_controls()` 一开头就判 `_in_replay()` ⇒ **「结束回合 / 重开 / 返回选人 / 暂停」四个按钮全部隐藏**
（对局暂停是 `tree.paused`，按了会把回放一起冻住；回放的暂停走控制条自己的那个），常驻「替补队伍」面板也收起；
退出回放只有控制条的「返回」。控制条贴在**屏幕下方**（原来在屏幕上方）。

**播放口径**：`_replay_loop()` 是**唯一**的推进者（按钮只写标志位/请求，不自己抢步骤）。
`_replay_end_frame()` 换段 = `_restore_snapshot(下一段)` → **停 1.5s 观察** → 报横幅（**不再按 `clip` 停**）；跳段 = 往后就地快进（`_replay_fast_forward`）、
往前回第 0 段重建再快进（`_replay_rewind`），快进期间把 `Engine.time_scale` 拉到 ≥60 ⇒ 演出照常播、墙钟极短（跑批用的也是同一招）。
**倍速** = `Engine.time_scale`（**1× → 2× → 4× → 0.5× → 1×** 循环；0.5× 是 2026-09-28 用户要求加的慢放档，
`replay_set_speed()` 的下限随之从 1.0 放到 0.5，按钮文字半档写「0.5×」）；**暂停** = 播放循环里等一个标志位（**不用 `tree.paused`**：那会把 HUD/按钮一起冻住）。

**这一版踩过的四个坑**（都在代码注释里留了原文，别再踩）：
① 跳段请求**必须排在主循环最前面**处理（原来是"已到末段就 break"之后 ⇒ 停在末段时点「上回合」没人处理）；
② 主循环演到末段会**正常收工** ⇒ 跳段要能**唤醒**它（`replay_seek_frame()` 里那句 `if not _replay_loop_running: _replay_start()`）；
③ 换段停顿**不能跟随暂停标志**（跳段途中用户可能正按着暂停 ⇒ 原来会永远等下去，`_replay_seeking` 一直为真、时间指针再也不动）；
④ 录像从 JSON 读回来时 **`Vector2i` 会变成字符串 `"(1, 3)"`** ⇒ 格子要过 `_fix_cell()`；`_do_move/_do_attack_obstacle/_place_sub`
三个动作入口的形参已改成 `Variant` 并在开头归一化（不这样改，回放里 AI 那一回合的走位会**整招作废**）；`rng.state` 存成十进制字符串
（JSON 存不下 64 位无符号整数，直接存会溢出失真）。

**部署逐手动画：点跳段不会再乱**（用户 2026-09-28 报「在部署阶段点击录像，部署人物会乱掉」）：
逐手上人是一段带 `await` 的循环（`_replay_deploy_frame()`），原来它只在两种情况下收手：
退出回放、或**正挂着**一个跳段请求。玩家在逐手上人途中点「开局 / 下回合」时，请求很快被消费掉

同时在重建局面 ⇒ 看着就是"人物乱掉"。

"仍在部署段（`_replay_frame == 0`）+ 跳段序号 `_replay_seek_seq` 没变过"⇒ 被接管的那趟当场停手。
✅ 实测：部署途中（场上 1 人时）点「下回合」→ 跳段落地到段 1、场上 6 人，4 秒后**仍是 6 人**（不再被塞人）；
点「开局」重演部署时全程峰值 5 人（≤6，无重影/乱序）。

再编成 JPEG（`JPG_QUALITY = 0.9`），按 **AVI(MJPEG)** 容器**边抓边写**一个 `.avi`
（落在**记忆的那一处**保存目录里，见 ⓪之二）—— 不用外部程序、不落盘帧序列、内存里只有当前一帧；
⚠️ **分辨率口径的两轮反复**（用户 2026-09-28）：先报「怎么这么大」⇒ 当时缩到长边 720（他的窗口 720×1280
被抓成 **405×720**）；随后报「**导出的 MP4 好糊啊**」⇒ 糊是**缩放**糊的（0.56× + 双线性 + JPEG 0.8），
现在改成**原生尺寸抓**（窗口长边 ≤1600 一律不缩；真缩也用 LANCZOS）、JPEG 0.9、x264 `-crf 18`。
中间那层 avi 因此变大（q0.9 ≈ 300~500KB/帧 ⇒ 两分钟 ~1~1.5GB），但它**转出 mp4 后就被删**（见第 ④ 条）
⇒ 最终交付的 mp4 体积不变。
⚠️ MJPEG 天生肥；要"又小又到处能播"只能转 **mp4/H.264（约 1/10）**，也就是下面第 ④ 条。
③ 帧率固定 **`FPS = 60`**（2026-09-28 用户报「录像帧率感觉不高」：先前的 30fps 是修「太快」时钉下的，
画面本身就是 30fps 的顿感），**导出期间把引擎帧率上限也钉到 60**（`Engine.max_fps = 60`，收尾还原），
再逐帧调 `Engine.time_scale`（`_drive_time_scale()`）：**让每一帧正好推进 `倍速 / FPS` 秒的游戏时间**
⇒ 视频重放出来的速度 == 观众当时屏幕上的速度（1× 就是实时；录的时候按 2×，视频里也是 2×）。
⚠️ **为什么必须钉上限（用户 2026-09-28 报「怎么默认倍速，太快了」·真因）**：抓帧是"每个渲染帧抓一张"、
AVI 又按 `FPS` 播，而"每帧推进多少游戏时间"全靠上面那个 `time_scale` 补偿 —— 机器渲染得比 `FPS` 快多少，
需要的 `time_scale` 就是那个倍数（60fps ⇒ 2.0、144fps ⇒ 4.8），而补偿原来有 `clampf(..., 0.1, 4.0)` 的上限
⇒ 高刷屏/关了垂直同步时**顶到上限**，每帧多推进一截 ⇒ 视频与屏幕上看到的导出过程一起"快了约 4 倍"。
钉到 `FPS` 之后稳态 `time_scale ≈ 1.0`（屏幕上看到的也正好是真实速度），上限同时放宽到 `8.0` 只为兜偶发卡顿；
⚠️ 机器渲染**跟不上 60fps** 时 `time_scale < 1` ⇒ 视频仍准时、只是屏幕上那趟导出看着变慢（标题里的
「实际 N fps」就是给这个读数用的）。
⚠️ **AVI 的 `RIFF size` 是 32 位** ⇒ 文件逼近 4GB 就会溢出成坏文件。60fps + 原生分辨率约 200KB/帧
⇒ 大约 5 分钟就到坎上，所以加了 `MAX_BYTES = 3.8GB`：到点**主动收尾**（已抓的部分照常转成 mp4），
另加 `MAX_FRAMES = 36000`（60fps × 10 分钟）兜帧数。
④ 本机有 ffmpeg（PATH / 项目内 `tools/ffmpeg.exe` /
winget·chocolatey·`C:\ffmpeg\bin`）就顺手转成更小的 `mp4`（H.264 / yuv420p / +faststart）并删掉 avi；

① `_begin_replay_from_store()` 里 **`_session_id += 1`**（与 `reset_match()` 同一手段）⇒ 那批旧协程

⇒ 下一步该盯的是**"阵亡触发的连带离场"那条路**（死灵法师 `on_died()` → `_skeletons_vanish()` →
`_skeleton_owner_gone()` 的淡出回调）在回放里是否照常走完，而不是招式本身。
✅ **加了诊断后查到的实情**：给那条路加了两个观测位（`Battle._obs_summon_log` 打开时生效，生产恒 false）——
`_on_unit_died()` 打印"谁死了/是不是召唤物/召唤主是谁/哪一段"，`_skeleton_owner_gone()` 打印"骷髅连带离场"。

"时序差"和"真错"分开）。⚠️ 但**段末**（已结算完）仍有真差异：局2 4/18 处（如第15段
回放 `0@3,2:h9` vs 录制 `0@3,3:h6`）⇒ 这部分**还没解释**，是下一轮的目标。
⚠️ **顺带发现的第二个 bug（未修）**：**进场**那一趟的第 0 段"回合开始那套"疑似**跑了两遍**

**回放里的"回合末清算"**（2026-09-28 真凶·已修）：逐步指纹反复报"**凭空多出若干 1 点血的己方单位**"
——那正是**死灵法师的骷髅兵**（`hero_33`，回合开始召唤、**回合结束即消散**）。实战 `_end_side()` 在"一方回合结束"
要跑一套清算（回合末技能 → 清状态 → 清刚结束那一方的墓碑 → 11 回合起烧血），**而那套的结果包含在下一段快照里**
⇒ 回放原本"本段演完直接跳下一段快照"，等于把这一套**整段跳过**：本段演完到换段之间，回放侧还留着本该当场
消散的骷髅，这一段的后续招也会与当时不一致（对面本该打的骷髅还在）。修法：新增 `_replay_side_end(idx)`，
在 `_replay_end_frame()` 里**换段前**按实战同一顺序跑一遍那套清算（不推进回合、不判胜负 —— 那些由下一段快照负责）。
✅ 复测：局3 **段末 0/20、逐步 0 段**（全清）；局1、局2 各降到 **段末 1 处**；「回合开始那套跑完 vs 录制侧
`frames[i].stage_fp`」三局均 **0 段不一致**（⇒ 回合开始技/召唤/补位那一层是准的）。
⚠️ 上一轮那处 `pd±1` **查明是指纹时点问题、已修**：逐步指纹是在"下一招被提交"那一刻写的，而阵亡计数挂在
`Unit.died` 上、比 `alive=false` 晚 0.3s（淡出）⇒ 手快时把"还没落账"的一刻记了下来。修法：**逐步指纹只记单位

段末 / `stage_fp` 这两处（它们都在"回合末排空死亡结算之后"取）。
✅ 再复测：局1 **段末 0/11、逐步 0 段**（全清）、局3 段末 1/20、局2 段末 3/15；「回合开始那套」三局仍 0 段不一致。

✅ **已定位到"打错人"并修（2026-09-28）**：逐步增量诊断（探针把"这一招改了什么"两边对撞）抓到
